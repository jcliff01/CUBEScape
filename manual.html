Operator's manual · version 1.2

CubeScope

A dashboard for the call records a Cisco CUBE writes. It puts each call's legs back together and shows how calls ended, who hung up, how the audio fared, and whether the records themselves are going missing on the way.

Cisco CUBE · IOS XE · gw-accounting syslog and file Single exe · .NET Framework 4.x · no install No database, no internet: the exe serves its own page

1What it is

A CUBE with accounting turned on writes one record for every call leg when that leg ends. It accounts each direction separately: the leg it answered from one side and the leg it placed to the other, and more legs for transfers and calls that loop back through it. On their own those records are hard to read. CubeScope reads them, joins the legs of each call back into one call, and shows what they say:

  • How calls ended, per minute, hour or day: answered, canceled while ringing, no answer, busy, rejected, failed.
  • Who hung up (the side whose leg disconnected first) and the cause that decided each call, in words.
  • Timings: ring time, talk time, and on dialer calls the gap between the customer answering and the agent side picking up.
  • Concurrent calls and legs, which is what the CUBE's licence counts.
  • Audio problems from the packet counts: no audio, one-way audio, a low packet rate. With the CUBE's quality figures turned on, MOS (the estimated voice quality score, 1 to 5), jitter and packet loss per leg.
  • Calls the records never show: calls the CUBE refused before placing any leg. Those are known only from its internal error message and its call-failure trace, which CubeScope keeps with the SIP INVITE inside it.
  • Everything else the CUBE sends: TLS failures, logins, configuration changes, licence messages.
  • Feed health: messages lost between the CUBE and the server, and legs whose records are incomplete.

Reads what the CUBE already sends

The hourly files a syslog server writes, the call record files the CUBE uploads over SFTP, or both. Nothing is installed on the CUBE and nothing polls it.

Every call opens to its evidence

Click a call for its legs, timeline, dial-peers, causes in words, quality figures, failure trace and the raw log lines it was built from.

Always on, if you want it

As a Windows service it keeps the newest day, raises alarms to the event log and SNMP traps, deletes old files and lets other computers in over HTTPS after a Windows sign-in.

2Install and build

There is nothing to install. CubeScope.exe is one file that needs only the .NET Framework 4.x every supported Windows Server already has. Copy it to the syslog server, the SFTP server or a workstation that can read their folders, and run it.

To build it from source, run build.bat in the project folder. It uses the C# compiler that ships with Windows (%WINDIR%\Microsoft.NET\Framework64\v4.0.30319\csc.exe), so it builds on a locked-down server too. build.bat test builds it and runs the built-in self-test, which must report no failures:

build.bat test
  bin\CubeScope.exe

CubeScope 1.2 self-test
  1697 passed, 0 failed

The dashboard page is built into the exe. It loads no web fonts and nothing from the internet, so it works on a server with no route out. This manual is the same: open manual.html straight from the folder.

3Quick start

The quickest way: double-click it

Double-click CubeScope.exe and a folder window opens. Pick the folder your syslog server writes the CUBE's files to, or the folder above several CUBEs' folders. CubeScope reads them, opens the dashboard in your browser on http://localhost:8792/ and keeps following new records. Keep the console window open while you use the dashboard; closing it stops CubeScope.

From a command prompt, the same in steps:

  1. Check what it finds. A summary on the console reads the files once and prints a table per day: calls, results, causes, media problems and missing messages. If it says it found no call records, see §4. 
    CubeScope.exe --logs D:\Syslog\192.0.2.10 --summary
  2. Serve the dashboard. Add --serve, and --open to open the browser. A folder holding one folder per CUBE gives you every CUBE, with a picker for one. 
    CubeScope.exe --logs D:\Syslog --serve --open
  3. Open it. http://localhost:8792/ on the same computer. For other computers, see §9.3.
What the CUBE needs

For syslog, two lines in its configuration: gw-accounting syslog (write a record per leg) and logging host <syslog server> (send them). Without the first, the files hold the CUBE's other messages but no calls. For call record files, see §4.2.

4Getting the records in

A CUBE can send its call records two ways. CubeScope reads either one, or both from the same CUBE at once, and treats a call the same whichever way it arrived.

FeedOn the CUBEWhat it gives
Sysloggw-accounting syslog and logging hostEvery leg's record and its numbers, transfers and forwards; internal errors and call-failure traces; configuration changes, logins and other events; numbered messages, so lost ones can be counted.
Syslog with figuresgw-accounting syslog stats and logging trap debuggingThe above plus a statistics block per leg: MOS, jitter, late and early packets.
Call record filesgw-accounting file, uploaded over SFTP or written to flashOne row per leg with Cisco's 133 columns: dial-peer, far-end media address, codec, the number as received and as sent, time to ringing, and the quality figures.

4.1Syslog files

Most syslog servers write one file per device per hour. CubeScope expects names like <name>-yyyy-mm-dd-hh.log, where the name is usually the CUBE's address. Other names work too and are grouped by folder. It looks two folder levels down, so a folder holding one folder per CUBE works.

OptionDefault
--days <n>14Read the newest n days. --all reads every file.
--from <t> --to <t>A range, as 2026-09-28 or 2026-09-28T14:00, on the CUBE's clock (or the one --zone names).
--cube <name>every CUBEOnly the CUBE whose files start with this name. Repeat it for several. Useful when routers and switches log into the same folder.
--pattern <glob>*.logWhich file names to read.
--threads <n>processors, at most 8How many files are read at once.

While serving, CubeScope keeps following the newest file of each CUBE and picks up new hours as they appear. --no-live reads once and stops.

The CUBE writes a record when a leg disconnects. A call that is still up is not in the files and does not appear until it ends.

4.2Call record files

With gw-accounting file the CUBE writes its records to files named cdr.<hostname>.<MM_dd_yyyy_HH_mm_ss.mmm> and uploads them over SFTP (or keeps them on flash). Point --logs at the folder they land in, alone or beside syslog files. New files are picked up about every 10 seconds. To set a Windows server up to receive them, use the Admin page (§9.2).

  • What they add. Tables by dial-peer, far-end media address and codec; Find pickers for dial-peer and codec; time to ringing; each number as received and as sent; every column by Cisco's name on a call; the same columns in the CSV; alarms on a dial-peer or a far-end address.
  • Quality. The quality columns are all zero unless the CUBE has media statistics, media bulk-stats, media stats-disconnect and call-quality under voice service voip. MOS and round trip also need RTCP (the far end's quality reports) from the far end. A call's detail then shows a Call quality table per leg, and the Ringing and call quality panel totals calls measured and calls rated poor (MOS under 3.5 or loss above 1%).
  • Many small files. Over SFTP a busy CUBE can start a new file every few seconds. That is expected; CubeScope reads them by name without listing the whole folder each time.
  • Old files. Settings deletes call record files older than a number of days you choose (§8).

4.3One CUBE sending both

Run both feeds and CubeScope shows one CUBE, not two. Syslog files are named by address and call record files by host name, and nothing in either names the other, so CubeScope pairs them by the calls they share.

  • How it knows. At least three legs must match exactly in both feeds: the same call ID, the same times to the millisecond and the same packet counts. If nothing matches, or the feeds cover different hours, they stay separate. Once paired, a leg counts as the same in both if its times are within 50 ms, because a real CUBE's two feeds differ by up to 10 ms.
  • What you get. Each leg once, under the host name, with what each feed adds: dial-peer, media address, codec and numbers from the files; jitter and MOS from syslog. A leg found in only one feed is kept. The call list's Data column shows which feeds each call came from.
  • Where to see it. Feed health shows the address the syslog arrives from and how many legs were in both feeds, syslog only and files only. Files only legs are records syslog lost; syslog only legs are records the file upload lost.
  • It remembers the pair in cube-links.json in the data folder. If an address is later given to a different CUBE, delete that file. A feed turned on while CubeScope runs joins within about five minutes.

4.4Files from flash, fetched every few minutes

If SFTP uploads lose records (§4.5), let the CUBE write its call record files to its own flash and fetch them with tools\Fetch-CubeFlashCdr.ps1, run as a scheduled task on the SFTP server. Each run logs in to the CUBE over SSH with a key, has it finish the file it is writing (file-acct flush with-close), and has the CUBE copy each finished file to this server as <name>.part. The script checks the size, gives the file its real name (CubeScope then reads it) and only then deletes it from flash. A file that does not arrive whole stays on flash for the next run. The newest file is never touched.

  1. In an administrator PowerShell on the SFTP server: .\Fetch-CubeFlashCdr.ps1 -Cube 192.0.2.10 -SftpServer 192.0.2.50 -Setup. It makes this server's SSH key (readable by administrators and SYSTEM only) and prints the CUBE configuration to paste: an account that logs in with that key, the SFTP login the CUBE uses for copy, file prompt quiet, and gw-accounting file writing to bootflash:cdr.
  2. -DryRun logs in, lists what it would move and changes nothing. Repeat until it lists the files.
  3. -EveryMinutes 5 -Install adds the task "CubeScope flash fetch", run as SYSTEM. -Uninstall removes it.
  • How often. Left alone the CUBE closes a flash file only after its file-close timer, at least 60 minutes. With the script a file is finished every run: 5 minutes is the suggestion, 1 minute works. Each run is a few SSH logins.
  • Folder and port come from this server's OpenSSH settings for the SFTP account (as the Admin page writes them), or from -Folder and -SftpPort. -SshOption 'PubkeyAcceptedAlgorithms=+ssh-rsa;HostKeyAlgorithms=+ssh-rsa' is for a CUBE that offers only the older RSA signatures.
  • Its log is %ProgramData%\CubeScope\FlashFetch\logs\flash-fetch.log (five files of 2 MB at most): each run, each file with its size, and why a file stayed on flash.
Not yet run against a real CUBE

-SelfTest runs the whole move against a pretend CUBE. Logging in with a key, copy started over SSH, and whether forcing a file closed loses records are still to be seen on a real one. Compare an hour of fetched files with syslog before relying on it.

4.5Known problem: SFTP uploads can lose records

On one customer's CUBE (a C8000V on IOS XE 17.12.4b, uploading to Windows OpenSSH), CubeScope and the CUBE's own debug output showed this:

  • Each upload wrote a file and then failed when the CUBE tried to add the records that had arrived meanwhile. The CUBE logged %VOICE_FILE_ACCT-3-DUMPFAIL and retried into a new file, so a busy CUBE leaves many small files.
  • Records that arrived during the retry were lost: in every case checked. The CUBE also dropped some on its own, logging file_acct buffer full. Drop msg.
  • The Windows server was not at fault: it accepted everything it was sent. Writing to flash instead lost nothing in an hour of comparison with syslog.
  • Changing maximum buffer-size did not stop it. Cisco lists two related defects (CSCwn19326, CSCwn13988) as fixed in 17.12.5a; that release was not tried.
What to do

Keep syslog accounting on beside the files: CubeScope fills the files' gaps from it, and Feed health counts the legs each feed missed. Or write the files to flash and fetch them (§4.4). To see the upload itself fail, use the Admin page's detailed SFTP logging (§9.4).

5.4Charts

Calls by result, Answered, Concurrent, Ring time, Talk time, Not answered, by cause, Media problems, Transfers and Answer to transfer connect plot the range over time. Media problems are also shown as a share of answered calls, because audio is only judged on answered calls.

  • Drag across a chart to zoom to that stretch; Back returns. Only a drag changes the time range. A single click never does.
  • Click a coloured band (on Calls by result, Not answered by cause, Media problems and Transfers) to keep only that band's calls over the same range. The band's clause goes into the filter, such as result=abandoned or result=unanswered cause=20, replacing any clause on the same field. Click the band again to take it off. Hovering says which band a click would take.
  • Click a legend entry to hide that series. Hiding Answered lets the failures use the whole height.

5.5Tables

  • Top called numbers, Top calling numbers, Top connected-to: each count with its share in grey (calls against every call in the range; not answered against that number's calls; bad audio against its answered calls). The last row adds up the rows listed. Click a number to filter the page to it.
  • Causes: every deciding cause with its name. Click a row to filter by it.
  • By dial-peer, By far-end media address, By codec: shown only when call record files are read.
  • Ringing and call quality: time to ringing, and calls measured and rated poor, when the CUBE sends figures.

5.6Canceled while ringing

Calls stopped before anyone answered. On a dialer call the dialer stopped it; on any other call the caller hung up. A bar chart has one bar per second the call ran before the cancel, from 0 to 120 seconds or more, with the dialer and callers in different colours. The table lists the piles: runs of seconds that each hold at least 1% of that side's cancels and at least 3 calls.

People hang up at scattered times, so a tall narrow pile is a machine's timer, such as a dialer campaign's no-answer timeout. Click a bar or a count to list those calls; the filter shows the clauses used, for example result=dialercanceled dur>=9 dur<11. --summary prints the same piles.

5.7Events and configuration changes

The Events lanes show everything the CUBE sent that is not a call record, over the range: internal errors, call-failure traces, TLS failures, logins, configuration changes, licence messages and the rest. Hover a mark for the message.

Below it are the last 10 configuration changes, from any time, not only the range shown: of all CUBEs or of the one picked. With archive log config on the CUBE they include the commands typed. The service keeps them in config-history.json, so they stay listed after its 24-hour window has moved on and after a restart.

5.8The call list

One row per call: start, duration, ring, talk, calling, called, connected-to, legs, result, released by, deciding cause, media, data, transfers and tags. Sort by any column. Click a number to filter by it; click the row for the call's detail.

  • Called is what the CUBE dialled on its first outbound leg, after its own number translation. Connected is the far end of the last leg to answer when that is not the number dialled, such as an agent's extension behind a routing label.
  • Released by is the far end whose leg disconnected first. Network means that leg's cause was a failure such as 41, 47 or 102.
  • Data says where the call's details came from: Syslog (the accounting messages), SFTP (the call record files) and Media (the CUBE sent media figures, even all zero). A dim label, like SFTP, means that source said nothing about the call; on a CUBE sending both feeds, that is a lost record.
  • Media shows the worst audio on a talking leg. On low rate and one-way it adds the packets a second sent and received on the leg that decided it (normal 20 ms audio is 50 a second each way). Hover for which leg.

5.10Clocks and time zones

Compares each CUBE's clock with the syslog server's. The server names each file by its own hour, so the times inside show how far ahead or behind a CUBE is. Whole hours are a time-zone difference; anything left over is a wrong clock, red when proven. A busy CUBE is pinned to within a second or two.

It also says which zone label the CUBE prints, whether the label matches its clock, summer-time mistakes (a winter label printed in July), and messages IOS marked * (clock never set) or . (NTP not in step). The server's zone is worked out from the CUBEs' labels, or set with --server-zone "Mountain Standard Time" (or UTC-6).

5.11Feed health

How complete each CUBE's records are:

  • Messages missing. IOS numbers every message it sends. A gap in the numbers is a message that never reached the file: lost in transit (syslog over UDP), or below the logging level. A lost call record shows up as a leg without its numbers record, or a numbers record with no leg.
  • Both feeds. The address syslog arrives from, and legs found in both feeds, syslog only and files only (§4.3).
  • Lines not used. Debug text outside failure traces, counted and skipped.

The note under it lists the number rules in use (Appendix A).

The same filter works in the page's filter box, in --filter on the command line and in --trace. Clauses separated by spaces must all hold; commas give alternatives; a ! in front reverses a clause.

7Alarms

Press Alarms in the top bar. Alarms run in the CubeScope service (§9.1), or in a CubeScope started with --alarms. Each alarm is sent once when the condition starts and its clear once when it ends, never repeated while it lasts.

What to watch

One row per thing to watch. Watch says which calls count; the number can match exactly, by its start or by its end.

WatchCalls countedJudged by
calledCalls whose first outbound number is this.The whole call
dialedCalls that arrived with this number.The whole call

  • CUBEs: tick the ones to judge; none ticked means every CUBE. Each CUBE is judged on its own.
  • Over % (default 1), Window (60 minutes), Min calls (50), Min failures (2). An alarm needs more than the limit, at least the minimum calls in the window and at least the minimum failures. One stray failure in a quiet hour is not an alarm, and a standby CUBE with no calls never is.
  • Counts as failed: rejected and failed by default; busy, no answer and canceled while ringing can be added. Canceled counts after N s (0 = every cancel) leaves out callers who hang up at once while catching a far end that never answers. It is measured from setup, because the records do not say when ringing began.
  • Note on the alarm: your own words for whoever receives it (who to call, which runbook), sent with the alarm and its clear.

How to raise it

Alarms on, check every N minutes, then the Windows Application log (Error or Warning), SNMP traps (one or more management stations, port, community, trap OID), or both. CubeScope builds and sends the trap itself over UDP (SNMPv2c), so the Windows SNMP service is not needed. The trap OID defaults to the placeholder 1.3.6.1.4.1.9999.1.3000; set your own.

No call records for N minutes raises an alarm per CUBE, and per feed on a CUBE sending both, when its call records stop. Set it longer than the quietest stretch: a record is written only when a call ends, and files arrive in batches. A CUBE that loses its SFTP server writes to flash and stays there until someone runs file-acct reset on it. Only real call records count, so a CUBE still sending other messages does alarm. A source is watched once a call record has been read from it; a stray log or a router in the same folder raises nothing.

Test alarm sends event 1000 plus a test alarm trap and, ten seconds later, its clear, on CUBE "TEST", so a test never closes a real alarm.

Last check and history

Last check shows every rule on every CUBE with its counts and state, and names anything not being watched. Alarm history lists every alarm, clear, warning and test sent, whether the event log took it and which addresses the trap went to (the newest 1,000 are kept). Open alarms survive a restart: a restart neither repeats an alarm nor forgets to clear it.

Press Settings in the top bar.

Delete old files

  • Delete syslog files older than N days and Delete call record (SFTP) files older than N days. 0 keeps them all, and that is the default. Deleting runs in the service or a CubeScope started with --alarms; a CubeScope run by hand says so and sends you to the service's page.
  • What goes. Only files named the way a syslog server or a CUBE names them, in the folder CubeScope reads (honouring --pattern and --cube, so another device's logs in a shared folder stay), up to two folders down, with their .sha256 check files. A file goes only when the hour in its name and its last change are both older than N days.
  • What stays. Any other name (such as … - Copy.log); the file being written; a file copied in recently. Folder links are not followed.
  • When. Once an hour, and at once when you save. A new or lower number takes a second press of Save, because deleted files cannot be brought back. The result shows as Last clean-up and goes in the log.
Keep N longer than the range you look at

Calls in a deleted file stay on the dashboard only until CubeScope restarts, and their raw log lines can no longer be opened.

9Running it on a server

9.1The Windows service

From an administrator command prompt on the server that holds the files:

CubeScope.exe --logs "D:\Syslog Server\Logs" --install-service

That creates the Windows service CubeScope and starts it. The Admin page's Keep CubeScope running as a service does the same. The service:

  • starts with Windows (delayed automatic start, as LocalSystem) and runs with nobody logged on. Windows restarts it if it stops on an error.
  • keeps each CUBE's newest 24 hours (--hours) and reads that window afresh every 6 hours, so its memory stays flat however long it runs: about 320 bytes a call leg, so a day of a busy pair of CUBEs is a few hundred MB.
  • answers this computer only on http://localhost:8792/, unless remote access is on (§9.3).
  • runs the alarms and the clean-up.
  • keeps its settings, alarm state and history in %ProgramData%\CubeScope and its troubleshooting log in %ProgramData%\CubeScope\logs.

It runs the exe from where it is, so put the exe somewhere permanent first. Run --install-service again to change the folder, the port (--serve 8793) or the hours; it updates the service in place and keeps the alarm settings. --uninstall-service stops and removes it; its settings and log stay. While the service holds port 8792, run CubeScope by hand on another port (--serve 8793) to look further back than 24 hours.

9.2The Admin page: receiving call record files over SFTP

The Admin page sets a Windows server up to receive a CUBE's call record files, with no commands to type.

  1. Copy CubeScope.exe to the server. If OpenSSH Server is not installed, put the openssh folder (Microsoft's installer) next to it.
  2. Right-click it, choose Run as administrator, and cancel the folder window. The Admin page opens in the browser (Edge or Chrome, not Internet Explorer). CubeScope.exe --admin does the same. In a CubeScope already open, Admin offers to reopen as administrator.
  3. Enter the settings: port (default 2121), folder (default C:\CubeCDR), account (default cube-cdr), password, and the CUBE addresses allowed. Review changes lists what will happen and changes nothing. Apply does it, stopping at the first problem.
  4. Paste the block shown at the bottom of the page on the CUBE.

Apply installs OpenSSH if needed, creates the account or changes its password, gives it write access to the folder, sets the port, limits the account to file transfer inside that folder, restarts OpenSSH and adds a Windows Firewall rule for those CUBE addresses only. OpenSSH's settings file is copied beside itself first (sshd_config.before-cubescope-…) and put back if OpenSSH rejects the new one. The page also shows the current state, the files received and recent sign-ins. Its steps go to %ProgramData%\CubeScope\logs. CubeScope never writes the password anywhere.

Who can use it

Only a window opened as administrator can make changes, only from the server itself, and only with the key in the link that window opens. The service runs as SYSTEM and answers anyone logged on, so it never does this work.

9.3Remote access: the dashboard from other computers (HTTPS)

By default CubeScope answers only the server it runs on. Remote access on the Admin page lets other computers open it over HTTPS on a port of its own: 8794 unless you choose another. Pick a port no other HTTPS program on the server uses; Apply refuses one that is taken.

  • Who gets in. People sign in with their Windows account; inside a domain the browser usually does it on its own. Only members of one local group (default CubeScope Users) and the server's administrators get in. Anyone else is told which group to ask to join. The Admin page and plain HTTP stay on the server only.
  • What Apply does. Makes CubeScope's own certificate, or uses one you choose by its thumbprint (for example from your company's certificate authority); creates the group and adds the people you list; binds the certificate to the port; adds a firewall rule (from anywhere, or only the addresses you list); saves the settings in remote.json; restarts the service; then checks that the port answers with that certificate and asks for a sign-in. Turn off removes the binding, the rule and the settings; the certificate and the group stay.
  • The browser warning. Browsers do not know a certificate CubeScope made, so they warn once. To stop that, use a certificate from your company's certificate authority, or import CubeScope's ("CubeScope HTTPS", in the server's Local Computer, Personal store) into the viewers' Trusted Root store.
  • It needs the service, which reads remote.json when it starts. Each person's first visit in an hour is noted in its log (who, from where). From an administrator prompt, --https <port> and --allow-group <name> do the same for a CubeScope run by hand, once the certificate is bound.
Tried so far

The Windows sign-in and the group check on this computer's own loopback (a member gets in, a non-member is refused, no sign-in is asked for one), and every Admin step against a stand-in. Not yet run on a real server: making and binding the certificate, the firewall rule, the group, and HTTPS itself.

9.4Detailed SFTP logging, for upload problems

When a CUBE reports %VOICE_FILE_ACCT-3-DUMPFAIL or stops sending, Detailed SFTP logging on the Admin page has OpenSSH write down every connection step and every file request (each write's size and OpenSSH's answer) for 15, 30, 60 or 120 minutes. Then it turns itself off, even with the page closed, and saves the lines to one text file you can download from the page. The files are kept in %ProgramData%\CubeScope\sftp-logs, readable by administrators only.

  • How. A marked block at the top of OpenSSH's settings file and a more detailed setting on the account's file-transfer command. The lines go to Windows' own OpenSSH event logs: CubeScope turns on OpenSSH/Debug (up to 256 MB) and lets OpenSSH/Operational hold 64 MB, noting how they were. It refuses with under 1 GB free on the system drive.
  • Turning it off, by the button or by a scheduled task that runs CubeScope.exe --sftp-logging-off as SYSTEM at the end time, takes the block out so OpenSSH's settings are exactly as before, restarts OpenSSH, saves the lines from a minute before it went on, and puts both event logs back as they were. Leave the exe where it is until then. Pressing Turn on again only moves the end time.
  • Each OpenSSH restart cuts off an upload in progress. The CUBE sends it again; if it moves to flash instead, run file-acct reset on it. For the CUBE's side at the same time: debug voip dump-file-acct (it reaches syslog with logging trap debugging), and undebug all afterwards.
Not yet tried on a real server

The switch is tested against a stand-in. The first real run will show whether this OpenSSH build writes its file-transfer lines to OpenSSH/Debug. OpenSSH never writes passwords to its log.

13How it works, and limits

How the calls are put together

Fact about the recordsWhat CubeScope does with it
The call ID is written three ways: with leading zeros dropped, padded, and cut to 12 characters in failure traces.All three are matched to one call.
A leg's numbers record follows its history record, sometimes in the next file.Gives the leg its calling and called numbers.
CallOrigin 2 is a leg the CUBE answered; 1 one it placed.In and out are told apart by this, never by order.
An unanswered leg has its connect time equal to its disconnect time.Answered means a placed leg connected before it disconnected.
On a refused call the inbound leg carries only the CUBE's generic 47.The outbound leg's cause decides the result.
The side that hangs up has its leg cleared first; the others follow within milliseconds.Released by = the far end of the leg that disconnected first, by time, not by order in the file.
Bridged legs mirror each other's packet counts.Audio is judged per talking leg; the dialer's signalling-only leg is never judged.
On a dialer call the customer leg counts no packets until the transfer.Its audio is judged from the transfer on.
IOS numbers every message it sends.Gaps are counted as messages missing.

DESIGN.md in the source has the measurements behind each of these, from a 10-day archive.

Speed and memory

On the reference archive (one CUBE, 10 days, 227 hourly files, 704 MB, 884,807 legs, 320,258 calls): read in about 6 seconds, about 290 MB of memory once read, never more than about 475 MB while reading, and a 10-day query in 0.3 seconds. That is roughly 320 bytes a leg. Only the records are kept; raw lines and a call's evidence are read back from the files when a call is opened. Events other than call records are capped at 100,000 per CUBE (counted beyond that). The console prints the memory in use after the read.

Security

  • A CubeScope run by hand answers localhost. Other computers get in only through remote access, over HTTPS, after a Windows sign-in, as a group member or administrator.
  • Anything that changes settings needs a header the page sends and the page's own address as origin, so another website cannot change them through your browser.
  • The Admin page works only from the server itself, in a window opened as administrator, with that window's key.
  • Passwords never go in a log, a settings file or a page answer. --trace and the raw lines show the CUBE's own messages as they are, and a CUBE's DUMPFAIL message can include the SFTP password in its address. Treat raw lines and reports from such a CUBE as sensitive.

Limits

  • A call appears only once it has ended.
  • The records do not say when ringing began, so ring time is from setup and canceled-after-N-seconds counts from setup.
  • Not yet run on a real server or CUBE: the HTTPS setup (§9.3), the detailed SFTP logging switch (§9.4), and the flash fetch script (§4.4). The Admin page's account creation and OpenSSH install have run only against a stand-in; its settings-file change, restart, firewall rule and answer check have run on a real server.
  • Quality charts have run only on invented figures; the filters and totals are built and tested.

ANumber rules

Legs can be labelled from their numbers, for filtering (tag=dialer) and to mark legs that never carry audio. CubeScope.exe --rules-sample prints the built-in rules; save them as cubescope.rules beside the exe (or pass --rules <file>) to change them:

signalling-only in cgn:""          the SIP dialer's leg has no calling number and no audio
tag dialer in cgn:""
tag cvp-label out cdn:555*
tag extension out peer:re:\d{4,6}
tag external peer:re:1?[2-9]\d{9}

Each line is an action (tag <name> or signalling-only), optionally in or out for the leg's direction, and a test on the calling number (cgn:), called number (cdn:) or far-end number (peer:), written as in the filters.
